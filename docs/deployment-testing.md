# Deploying the testing environment

The testing environment runs on [Render](https://render.com): a web service for the Next.js app, a web
service for the NestJS API (with background workers running inside it), and a PostgreSQL database. File
storage is any S3-compatible bucket. Production runs on the client's own server and is covered in
Release 4.

Everything is described in `deploy/render.yaml`. The application reads all configuration from
environment variables and **refuses to start** when one is missing or invalid (the message names the
variable and never prints its value).

## 1. Before you start

You need:

| What                                                                           | Why                                    |
| ------------------------------------------------------------------------------ | -------------------------------------- |
| A Render account and this repository connected to it                           | hosts the services                     |
| An S3-compatible bucket and its keys (AWS S3, Cloudflare R2, Backblaze B2 ...) | product images, documents, attachments |
| Two RSA keys and a note of the two service addresses                           | token signing and CORS                 |

Generate the token-signing key pair on your own machine (never commit it):

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out jwt-private.pem
openssl rsa -in jwt-private.pem -pubout -out jwt-public.pem
```

## 2. Create the services

1. In Render choose **New → Blueprint** and select this repository and the file `deploy/render.yaml`.
2. Render creates `bms-db`, `bms-api` and `bms-web`. The first sync stops to ask for the variables marked
   `sync: false`. Fill them in:

| Variable                                                                  | Service | Value                                                                                                                                       |
| ------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `JWT_PRIVATE_KEY`, `JWT_PUBLIC_KEY`                                       | api     | the contents of the two `.pem` files. Paste as one line, writing each line break as `\n` (or paste the multi-line value; both are accepted) |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_REGION` | api     | from your bucket provider                                                                                                                   |
| `WEB_ORIGIN`                                                              | api     | public address of `bms-web`, e.g. `https://bms-web.onrender.com` (no trailing slash)                                                        |
| `API_BASE_URL`                                                            | api     | public address of `bms-api`, e.g. `https://bms-api.onrender.com`                                                                            |
| `META_APP_SECRET`, `META_WEBHOOK_VERIFY_TOKEN`                            | api     | any non-empty placeholder for now; real values are needed at the messaging phase                                                            |

`INTEGRATION_ENCRYPTION_KEY` is generated by Render. `REDIS_URL` is a placeholder until the messaging
phase adds a key-value store.

Other values in the file are deliberate: `APP_ENV=testing`, `STORAGE_DRIVER=s3`,
`WORKERS_IN_PROCESS=true`, `ALLOW_PUBLIC_SIGNUP=false` (new businesses are created by an operator),
`SEED_ALLOW_PRODUCTION=false`.

## 3. What happens on every deploy

1. Render builds the app (`turbo run build`), which also generates the database client.
2. **Before** the new version takes traffic, `prisma migrate deploy` applies pending migrations. If a
   migration fails the deploy stops and the previous version keeps running.
3. The API starts and Render calls `GET /api/v1/health/ready`, which checks the database and the file
   storage. The web service is checked on `/login`.
4. `autoDeployTrigger: checksPass` means a deploy starts only after the CI checks (lint, type check,
   tests, secret scan) pass on the commit.

## 4. First data

Open a shell on the `bms-api` service (Render dashboard → Shell) and run:

```bash
cd apps/api
# the demo business, with one sign-in per role. Prints a generated password unless you pass --password
node dist/cli/seed-demo.js
# or, a real business without demo data:
node dist/cli/workspace-create.js --name "Acme Furniture" --owner-email owner@acme.example \
  --owner-first Ada --owner-last Owner --currency PKR --timezone Asia/Karachi
```

`seed-demo` is safe to run again (it adds only what is missing) and refuses to run when
`APP_ENV=production` unless `SEED_ALLOW_PRODUCTION=true`. Pass `--reset-passwords` to give the demo users
a new password. All demo data is synthetic. It includes a sample catalog: the furniture categories and 30
products with colour variants, dimensions, material and finish attributes, alternative names and placeholder
images.

The demo business has these sign-ins (all with the printed password): `owner@demo.test`,
`manager@demo.test`, `salesperson@demo.test`, `cashier@demo.test`, `inventory@demo.test`,
`accounts@demo.test`, `production@demo.test`, `automation@demo.test`, `viewer@demo.test`.

## 5. Checking it works

1. `https://<api>/api/v1/health/ready` answers `{"data":{"status":"ok","checks":{"database":"up","storage":"up"}}}`.
2. `https://<web>/` redirects to the sign-in page; signing in as the Owner shows the home page.
3. Each role sees only the menu entries its permissions allow.
4. Upload a file (for example a company logo in Settings → Business) and open it: this proves the bucket works.

## 6. Rolling back

Render keeps previous deploys. To go back, redeploy the previous successful deploy of the service. If
the failed release already applied a migration that the old code cannot work with, run that migration's
`rollback.sql` (stored next to it in `apps/api/prisma/migrations/<name>/`) against the database first.
Every migration has one.

## 7. Rotating secrets

- **Token keys:** generate a new pair, replace both variables, redeploy. Everyone has to sign in again.
- **S3 keys:** create new keys at the provider, update the two variables, redeploy, then delete the old keys.
- **`INTEGRATION_ENCRYPTION_KEY`:** do not change it once integrations are connected, because stored
  channel and AI credentials are encrypted with it; reconnect each integration after a change.

## 8. Backups

The Render database has platform snapshots. Before the client's acceptance test, take a manual backup
and rehearse a restore into a scratch database; record the date in `docs/known-limitations.md`
(task 85).
